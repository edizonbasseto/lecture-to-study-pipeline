# 0013. LLM Mock Exam Generation (Forced JSON Extraction + Retry)

## Status

Accepted. **Superseded by ADR 0038:** the local llama.cpp exam generator (exams/generator.py) is deleted; exams are generated by scripts/generate_codex_mock_exam.py (ADR 0030) and orchestrated as a child process. The deterministic compiler survives. The erratum below is historical. **Erratum (ADR 0020):** the llama-cli invocation referenced
below uses `--json-schema`, a flag name confirmed wrong running the real
pipeline end to end -- the correct flag is `--json-schema-file`, and the
call site now also passes `-n` to cap completion length. See ADR 0020 for
the corrected contract and the incident that found it. Every other
decision recorded here is unaffected.

**Erratum (ADR 0022):** `--json-schema-file` itself was subsequently
dropped entirely (this llama-cli build's grammar sampler fails to
initialize on any structured-output request, a known upstream defect) in
favor of embedding the schema as prompt text plus post-hoc parse/validate.
This ADR's own Critic/Repair retry (already present) is unaffected. See
ADR 0022 for the full incident and rationale.

**Erratum (ADR 0027):** the prompt no longer names its input "Evidence
Pack" -- the first real run showed the model addressing the student
"according to the Evidence Pack" in every question, and writing eleven of
twelve questions in English. The instruction now demands pt-BR and forbids
referring to the source material, and a deterministic guard fails the run
on either defect. See ADR 0027.

## Context

Phases 10-12 stayed deliberately off the LLM: Markdown/HTML publishing
(Phase 10-11) and the Anki deck (Phase 12) are both pure data
transformations over already-vetted `LectureGlobalIndex`/
`CanonicalLectureDocument` content, explicitly to avoid re-deriving text
an LLM could paraphrase into a hallucination.
`.prompts/fase13_mock_exams.md` asks for something structurally different:
a 5-question multiple-choice clinical mock exam, which is not a fixed
transformation of already-extracted facts but a new synthesis task (write
a clinical scenario, four plausible options, and a justification) that
only a generative pass can produce. Phase 13 therefore returns to the
local llama.cpp (Metal, Apple Silicon) inference path Phases 5-7
(`semantic`, `drafting`, `critic`) established, applying the same
"evidence-grounded, JSON-schema-constrained, retry-on-broken-contract"
discipline those phases already use, one step later in the pipeline.

## Decisions

1. **`MockQuestion`/`MockExam` domain models** (`domain/models.py`,
   appended after `Flashcard`): `MockQuestion` holds `question_text: str`,
   `options: dict[str, str]`, `correct_answer: str`, `explanation: str`,
   `model_config = ConfigDict(strict=True)`, plus two `after`-mode
   `model_validator`s: `options` must have exactly the keys `A`/`B`/`C`/`D`
   (the instruction's own four-alternative example, `{"A": "...", "B":
   "...", "C": "...", "D": "..."}`, taken as a hard cardinality contract,
   not just an example shape) and `correct_answer` must be one of
   `options`' own keys -- an MCQ with too few/many options, or an answer
   key that does not name a real option, is a broken contract at the
   domain level, not just a formatting nit, so both are rejected at the
   same Pydantic boundary as every other structural check in this file
   (e.g. `CanonicalLectureDocument`'s `total_units`-matches-`units`
   validator). `MockExam` holds `lecture_id: SafeIdentifier` and
   `questions: list[MockQuestion]`.
2. **`MockExamGenerationError`** (new, `domain/errors.py`): raised by
   `exams/generator.py` for both categories the instruction names --
   "falhas na inferência" (subprocess missing/non-zero-exit) and "quebra
   de contrato JSON do LLM" (unparseable output, wrong-shaped array, a
   `MockQuestion` failing its own `options`-cardinality or
   `correct_answer`-in-`options` check) -- whenever the original attempt
   and its single repair retry both fail. Placed in `domain/errors.py` per
   the instruction's explicit text, even though ADR 0008's own
   domain-policy-vs-technical criterion (a validation gate on a
   cross-field invariant belongs here; "a technical/IO failure local to
   one worker" does not) would put the subprocess/parse-failure half of
   this class's trigger set back in a module-local `LlmParsingError`
   instead, matching `drafting`/`semantic`/`critic`. See this class's own
   docstring in `domain/errors.py` and Alternatives Considered below for
   the full argument on both sides.
3. **`MockExamGenerator.generate_exam`** (`exams/generator.py`):
   - Validates `lecture_id` as a `SafeIdentifier` before any `Path` splice,
     matching every other phase's convention.
   - Reads
     `workspace/data/10_canonical_documents/{lecture_id}/canonical_document.json`
     directly (not via a sibling orchestrator), raising the pre-existing
     `LectureNotFoundError` if absent -- the same file `publishing/
     pipeline.py` (Phase 11) already guards, reused rather than
     duplicated, matching ADR 0008's own anticipated extension path.
   - Builds the Evidence Pack as the `\n\n`-join of
     `document.units[*].content.body_markdown`, in the document's own
     already-chronological (`pack_sequence`) order -- no re-sorting.
   - Prompts a local llama.cpp (Metal) subprocess, grammar-constrained via
     `--json-schema` to `TypeAdapter(list[MockQuestion]).json_schema()`
     (an array schema, not a single-object one, since the instruction asks
     for "um array JSON validável" directly -- no `lecture_id`-envelope
     object the LLM would need to echo back for a traceability check, the
     way Phase 6's `LearningUnitDraft` does).
     The instruction text is explicit that the model must never fall back
     on outside veterinary knowledge, and must instead write questions
     about whatever the lecture *does* cover if it is thin on a topic --
     both constraints are stated verbatim in the prompt.
   - Parses stdout by scanning for balanced, string-literal-aware
     top-level `[...]` spans (the array-shaped sibling of `drafting`/
     `semantic`/`critic`'s own `_iter_balanced_object_spans`, since this
     phase's target is a JSON array, not a single object) and validating
     each candidate against `list[MockQuestion]`, tracking a
     wrong-question-count candidate separately from a genuine
     `ValidationError` so the raised message names the actual failure
     instead of a generic "nothing parsed".
   - **Critic/Repair retry (1 attempt):** exactly as the instruction
     specifies -- any failure (subprocess-level or JSON/Pydantic-contract
     level) on the first attempt triggers exactly one more attempt, this
     time with the first failure's message appended to the prompt as
     repair feedback; a second failure raises `MockExamGenerationError`
     and gives up. No `CriticOrchestrator`-style separate evaluator model
     pass (Phase 7's own two-model critique step) -- the instruction
     scopes this retry to the JSON/Pydantic contract specifically, not a
     second clinical-grounding review pass.
4. **`ExamCompiler.compile`** (`exams/compiler.py`, kept as its own module
   rather than folded into `generator.py`, matching `publishing/`'s own
   precedent of a dedicated file for rendering/persistence separate from
   the module that produces the data -- though the split boundary itself
   differs: `publishing/markdown_compiler.py`'s `MarkdownCompiler.compile`
   is a pure transform (document+index in, Markdown string out) with all
   file I/O owned by `PublishingOrchestrator` in `publishing/pipeline.py`,
   whereas `ExamCompiler.compile` here owns its own `exam.json`/
   `simulado.md` writes directly, since Phase 13 has no separate
   orchestrator module to own them instead):
   persists `workspace/data/14_mock_exams/{lecture_id}/exam.json` (raw
   `MockExam.model_dump(mode="json")`) and
   `workspace/data/14_mock_exams/{lecture_id}/simulado.md` -- a
   questions-and-alternatives section (options rendered in sorted
   `A`/`B`/`C`/`D` letter order regardless of the LLM's own JSON key
   order), a `---` divider, then a "Gabarito e Justificativas Clínicas"
   answer key. Both files are written via the codebase's established
   write-`.tmp`-then-`replace` atomic pattern.

## Rationale

- **Why a JSON *array* schema instead of an object envelope echoing
  `lecture_id` (unlike Phase 6's `LearningUnitDraft.lecture_id`/
  `pack_sequence` traceability echo).** The instruction's own wording asks
  for "um array JSON validável", and a mock exam has no `pack_sequence` to
  cross-check in the first place -- `lecture_id` is supplied by the caller
  (`generate_exam`'s own argument) once the array is validated, not
  round-tripped through the model's own output, so there is nothing for
  an echo-based traceability check to verify here.
- **Why the retry is scoped to the JSON/Pydantic contract, not a second
  clinical-grounding critique.** The instruction is explicit: "1 tentativa
  de retry se o JSON falhar no parse do Pydantic". Phase 7's
  `CriticOrchestrator` (a second model pass judging hallucination against
  the Evidence Pack/Ledger) is a heavier mechanism the instruction does
  not ask this phase to reuse; adding it would be scope beyond what was
  requested, on top of doubling local GPU/VRAM cost for every exam
  generated.
- **Why `MockQuestion` validates `correct_answer` against `options` at the
  Pydantic boundary instead of leaving it to `exams/compiler.py` to check.**
  A JSON payload that parses as valid `list[MockQuestion]` shape-wise but
  names a non-existent answer key is exactly the kind of "quebra de
  contrato" the instruction's retry loop exists to catch -- catching it at
  parse time (so it raises `ValidationError`, which `_parse_questions`
  already treats as a retry trigger) means one validation path covers both
  shape and this specific cross-field invariant, instead of a second,
  compiler-side check that could pass a broken exam through undetected if
  ever called without going through the generator first.
- **Why `options` is constrained to exactly the keys `A`/`B`/`C`/`D`,
  not just validated for `correct_answer`-membership.** A
  `principal-code-reviewer` and `staff-architect` pass on this ADR's first
  draft both independently flagged the same gap: the original model only
  checked that `correct_answer` named a real option, so a 2-option or
  10-option response, or one keyed `"opt1"`/`"opt2"`, would still pass.
  The instruction's own example JSON is a 4-key `A`-`D` mapping, and
  `exams/generator.py`'s prompt already asks the LLM for exactly that
  shape -- pinning it as a domain invariant closes the gap at the same
  Pydantic boundary the `correct_answer` check already uses, rather than
  leaving a wrong-cardinality response to render as a visibly broken
  multiple-choice question in `simulado.md`.
- **Why `_parse_questions` prioritizes a wrong-question-count match over a
  `ValidationError` from some other span when both occur in the same
  stdout.** A `principal-code-reviewer` pass on this ADR's first draft
  found the original ordering did the opposite (a later span's parse
  failure could mask an earlier, shape-valid-but-miscounted array's more
  actionable message). A shape-valid array that merely has the wrong
  question count is the more likely candidate for "the real answer, just
  miscounted" than an unrelated malformed fragment (banner noise, a stray
  bracketed token) elsewhere in the same stdout, so it now wins.
- **Why `simulado.md` escapes `question_text`/`options`/`explanation` the
  same way `publishing/markdown_compiler.py` escapes LLM-extracted free
  text.** This phase's own review-board precedent (Phases 10-11 closed an
  HTML-injection and an embedded-newline-block-injection finding on
  exactly this class of "LLM free text interpolated into a structured
  output format" risk) applies proactively here rather than waiting for a
  finding: a stray `#`/`*`/blank line in a generated question or
  explanation must not spoof a heading or fracture `simulado.md`'s
  structure.

## Consequences

- `domain/models.py` now holds a fifth and sixth lecture-scoped output
  model (`MockQuestion`, `MockExam`) alongside `LectureMetadata`,
  `LectureGlobalIndex`, `CanonicalLectureDocument`, `Flashcard` -- four
  prior models, so the new pair is fifth/sixth (corrected during Phase
  14's review board: a `docs-consistency-auditor` pass on ADR 0014's
  first draft found this same off-by-one pattern had propagated from
  here).
- `domain/errors.py` gains `MockExamGenerationError` as a `RuntimeError`
  directly (not a `LectureNotFoundError` subclass, unlike Phase 12's
  `GlobalIndexNotFoundError`): it guards a structurally distinct
  condition -- inference/JSON-contract failure, not a missing upstream
  artifact -- so there is no shared base class for a caller to usefully
  collapse the two under.
- Phase 13 is llama.cpp's fourth call site in this codebase (after
  `semantic`, `drafting`, `critic`), and duplicates that convention's
  `_write_temp_file`/`_start_llama_process`/balanced-span-scan machinery
  locally rather than importing it from `drafting/llm_worker.py`, per ADR
  0006's established self-containment rule -- ADR 0006's own literal text
  scopes that rule to `domain.models` only ("imports only from
  `domain.models`, never a sibling phase module"); Phase 13 additionally
  imports `domain.errors` (`LectureNotFoundError`,
  `MockExamGenerationError`), which every phase since Phase 9 already does
  without treating it as a sibling-phase reach-in, since `domain/errors.py`
  is itself domain-layer, not another phase's internals. This now being
  llama.cpp's fourth independently-duplicated worker crosses the informal
  "rule of three" threshold; worth a deliberate future ADR (a shared base
  vs. reaffirming ADR 0006) rather than silent accretion at a fifth call
  site, but out of this ADR's scope.
- `exams/` reaches 100% statement coverage with all subprocess calls
  mocked (`FakeProcess`/`monkeypatch`, matching `test_drafting.py`'s own
  pattern), including the retry-then-succeed, retry-then-fail,
  wrong-question-count, missing-binary/non-zero-exit, and
  string-literal-aware bracket-scanning (a bracket inside a quoted
  `explanation`/`option` value, and banner noise containing bracket
  tokens ahead of the real array) branches -- the last of these added
  after a `principal-code-reviewer` pass on this ADR's first draft found
  the array scanner's string-literal-awareness itself had no regression
  coverage (deleting it left the suite green).
- `domain/errors.py`'s module docstring and `LectureNotFoundError`'s own
  docstring are updated to list Phase 13's new call sites, per this
  file's own established "docstring is the authoritative site list"
  convention (`docs-consistency-auditor`).

## Alternatives Considered

- **A module-local `LlmParsingError` in `exams/generator.py`, matching
  `drafting`/`semantic`/`critic`'s own convention, instead of
  `MockExamGenerationError` in `domain/errors.py`.** This is the
  codebase's actual precedent for every prior inference-failure exception,
  and `domain/errors.py`'s own module docstring frames the file as
  existing for upstream-handoff-artifact-*existence* guards specifically
  (`LectureNotFoundError` and its relatives), not inference failures. A
  `staff-architect` pass on this ADR's first draft pressed this point
  further, engaging ADR 0008's own domain-policy-vs-technical criterion
  directly (a criterion this ADR's first draft cited but never actually
  applied): ADR 0008's Consequences anticipates this file being extended
  for a *domain-policy* validation, explicitly contrasted with "a
  technical/IO failure local to one worker" -- and `MockExamGenerationError`'s
  trigger set is mostly the latter (missing binary, non-zero subprocess
  exit, unparseable stdout), with only the `options`-cardinality/
  `correct_answer`-membership case actually being domain policy, and that
  case is already caught by `MockQuestion`'s own `model_validator` raising
  a plain `ValidationError`, not by `MockExamGenerationError` at all. By
  that criterion, a module-local `LlmParsingError` would be the more
  architecturally consistent choice, mirroring the one-caller,
  zero-cross-phase-catcher blast radius `drafting`/`semantic`/`critic`
  each keep local. Not taken anyway: the Phase 13 instruction names
  `MockExamGenerationError` explicitly and places it in `domain/errors.py`
  by its own text ("Em `domain/errors.py`, crie `MockExamGenerationError`"),
  the same literal-instruction-honoring precedent ADR 0012 already set for
  `GlobalIndexNotFoundError` -- the operator's explicit instruction is
  weighted over the architectural criterion here, as it was there, and
  this ADR records the tension rather than silently resolving it in the
  instruction's favor. A future phase citing this ADR as precedent for
  extending `domain/errors.py` with another technical/IO failure class
  should not treat this decision as endorsing that criterion having been
  satisfied -- it was not; only the literal instruction was.
- **A separate `LlmParsingError` for subprocess/parse failures, reserving
  `MockExamGenerationError` for the exhausted-retry case only.** Considered
  to mirror `drafting/llm_worker.py`'s two-layer shape (`LlmParsingError`
  raised internally, wrapped by a caller into a domain-level failure).
  Rejected: the instruction's own text covers both "falhas na inferência"
  and "quebra de contrato JSON" under the one name it gives, and Phase 13
  has no second orchestrator layer (unlike Phase 7's `CriticOrchestrator`
  wrapping `drafting`'s `LlmParsingError`) that would need a distinct
  inner type to catch separately from the outer one.
- **Enforcing exactly 5 questions via a `Field`-level constraint on
  `MockExam.questions` (e.g. `min_length=5, max_length=5`) instead of a
  runtime check in `_parse_questions`.** Considered for symmetry with
  other domain-level count constraints (e.g. `CanonicalLectureDocument`'s
  `total_units` validator). Rejected: `MockExam` itself has no reason to
  forbid a differently-sized exam in general (a future phase could
  reasonably want a 10-question or 3-question variant); the "exactly 5"
  requirement is this generation pass's own prompt contract, not an
  invariant of the `MockExam` domain concept, so it is enforced where the
  contract is made (the generator's parse step) rather than baked
  permanently into the shared model.
- **`MockExam.lecture_id: str` (the instruction's literal type) instead of
  `SafeIdentifier`.** Not taken, and -- a `docs-consistency-auditor` pass
  on this ADR's first draft flagged that this substitution went
  unrecorded here despite this ADR citing ADR 0009's own precedent
  (Alternatives Considered, above the `GlobalIndexNotFoundError` bullet)
  for flagging exactly this kind of literal-instruction deviation --
  `SafeIdentifier` is used instead, matching every other phase's
  `lecture_id` field (`LectureMetadata`, `EvidencePack`, `SemanticLedger`,
  `LearningUnitDraft`, `ValidatedLearningUnit`,
  `CanonicalLectureDocument`). A bare `str` field would accept a
  `../`-containing value at construction time, deferring the path-
  traversal guard entirely to `generate_exam`'s own
  `_LECTURE_ID_ADAPTER.validate_python` call and leaving `MockExam`
  itself unable to guarantee its own `lecture_id` is filesystem-safe if
  ever constructed another way (e.g. directly in a test, or by a future
  caller) -- the same reasoning `SafeIdentifier`'s own definition in
  `domain/models.py` states for every other model that carries this
  field.
